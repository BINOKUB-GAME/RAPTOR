Chantiers de Développement Ouverts

Les fronts d'ingénierie sur lesquels vos compétences peuvent faire la différence immédiatement.

BUG

Banc d'Essai & Traque de Bogues

Éprouver la suite logicielle (raptor, rap, rapless) sur divers noyaux et distributions Linux (Debian, Arch, RHEL, Alpine musl, Ubuntu). Repérer les fuites mémoire résiduelles avec Valgrind et corriger les comportements limites sous stress.

COMPÉTENCES : C99, GDB, Valgrind, POSIX
MEM

Registres de Souveraineté

Maintenir et affiner mem_whitelist.conf pour neutraliser les faux positifs induits par les nouveaux moteurs JIT (V8, WebKit, Dart) et les couches d'émulation (Wine, Proton, Flatpak), sans jamais dégrader la sensibilité face aux vrais shellcodes Inode 0.

COMPÉTENCES : Forensic Linux, /proc maps
NET

Flux C2 & Threat Intel

Enrichir le registre fw_officiel.conf avec les plages d'infrastructures malveillantes avérées (relais Cobalt Strike, serveurs C2 actifs, nœuds d'exfiltration furtifs) et optimiser la résolution BGP/ASN locale.

COMPÉTENCES : Réseaux IPv4/IPv6, CIDR, Net-Guard
MOD

Nouveaux Greffons d'Audit

Développer de nouveaux modules respectant l'interface RaptorPlugin : détection des canaux cachés ICMP, inspection eBPF des appels système furtifs, ou surveillance d'intégrité des modules noyau (LKM rootkits).

COMPÉTENCES : Noyau Linux, Greffons C isolés

Norme d'Ingénierie & Rigueur du Code

Aucun code "bouclé à la va-vite". Le projet applique une discipline chirurgicale pour garantir la fiabilité opérationnelle sur les systèmes de production.

1. Standard C99 Strict & Survie 0 Heap

Les outils de la trousse CLI (rap et rapless) doivent s'exécuter sans aucune allocation dynamique (malloc/free proscrits). Les tampons sont strictement bornés sur la pile d'exécution.

2. Modularité & Greffons Isolés

Chaque nouvelle sonde d'inspection doit être implémentée sous forme de composant indépendant sans jamais altérer le cœur central. Les extensions s'enregistrent via le bus ou la table déclarative.

3. Documentation & En-têtes Numérotés

Chaque fichier source doit comporter obligatoirement son cartouche normalisé : nom du script, numéro de révision, bloc descriptif des nouvelles intégrations et énumération exhaustive de chaque fonction numérotée.

4. Gardes-fous & Codes POSIX

Toute fonction cinétique doit vérifier le garde-fou rap_check_safety_pid. Chaque utilitaire doit renvoyer rigoureusement les codes de sortie POSIX normalisés (0 = Sain, 1 = Menace, 2 = Erreur).

Flux de Contribution Git

Processus standard pour soumettre une correction de bogue ou proposer une nouvelle fonctionnalité.

bash — Cycle de contribution standard
# 1. Créer une branche dédiée pour votre correctif ou greffon git checkout -b feature/nom-de-votre-sonde # 2. Compiler en mode Debug pour activer les contrôles de sécurité cmake -B build -DCMAKE_BUILD_TYPE=Debug cmake --build build # 3. Vérifier le comportement unitaire ./build/rap hunt # 4. Rédiger un commit explicite avec numéro de révision git commit -m "Rev 1.1: Intégration de la fonction 111 (audit_ebpf)" git push origin feature/nom-de-votre-sonde

Divulgation Responsable des Vulnérabilités (Security Advisories)

Si vous découvrez une vulnérabilité critique affectant l'intégrité de l'hôte ou une méthode de contournement des sondes mémoire de RAPTOR, ne créez pas d'Issue publique.

Transmettez directement votre rapport technique chiffré via notre canal de sécurité dédié sur GitHub Security Advisories pour permettre à l'équipe de publier un correctif coordonné.
